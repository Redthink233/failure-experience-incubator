## 1. Q12｜用户能否手动晋升 / 撤销 `accepted` Insight

### 1.1 问题与既有约束

> **问题**：用户是否可以自行把任意 `candidate` 直接变成 `accepted`（手动晋升），以及是否可以撤销已经 `accepted` 的 Insight？

既有约束（不得重开、不得绕过）：

| 依据 | 约束 |
|---|---|
| **D-015** | `Experience Asset` 只是 `accepted` Insight 的产品视图；状态集为 `candidate` / `accepted` / `rejected`，**不新增状态** |
| **D-021** | **E1–E5 为硬条件**；E5 = 用户显式接受；**E1（≥1 条 `Formal Attempt`）/ E4（证据可追溯）不得被绕过** |
| **D-022** | `Candidate Insight` **只在第 ⑧ 步生成**；不建 candidate 待办池 |
| **D-014** | 决策型 / 持久化 `Inference` **必须由用户显式接受或拒绝**；`accepted` 后来源仍为 `Inference` |
| **D-021 特别确认** | **C4′ / C5′ 仅作增强信息，不打分、不设等级**；**跨记录比较不是硬门槛** |
| **D-037 三问检验** | 任何数字 / 门槛须通过"是否自动解锁更强结论 / 是否自动提升可信度表述 / 是否绑定输出内容量"三问；**本项不引入任何计数或阈值** |

### 1.2 方案比较

| 维度 | **方案 A**：可随时手动晋升 + 可撤销 | **方案 B**：可撤销；**晋升仍须 E1–E5** | **方案 C**：V1 不允许撤销 / 手动处理 |
|---|---|---|---|
| 机制 | 任意 `candidate` 可被用户一键置为 `accepted` | 系统检查 E1–E4 并显式呈现缺失项；**用户只能对已满足 E1–E4 的 candidate 执行接受（= E5）**；已 `accepted` 的可撤销回 `candidate` | 只有第 ⑧ 步的一次性接受；接受后不可撤销、不可再处理 |
| 与 **D-021** 一致性 | **冲突** —— 用户可绕过 E1–E4，E1–E4 被降级为"建议" | **一致**（强化） | 一致（但过度收紧） |
| 与 **D-015** 一致性 | 一致（状态集不变） | 一致（撤销 = `accepted → candidate`，**不新增状态**） | 一致 |
| 与 **D-014** 一致性 | 一致 | 一致（撤销是用户行为，不是新的 `Inference`） | **弱冲突** —— 决策型 Inference 要求"接受**或拒绝**"，且 D-015 有 `rejected` 态；C 使用户在接受后改变主意时**没有可表达的状态**（改用 `rejected` 会表达成"我认为这条结论不成立"，语义错误） |
| 与 **D-022** 一致性 | 一致（不新增生成时机） | 一致 | 一致 |
| 用户价值 | 高（但把"经验层"变成用户自定标签） | **高** —— 用户可以表达"我现在不再把这条当作可复用经验"，而无需贬低它 | 低 |
| AI 可信度 | **低** —— "经验资产"不再意味着"有证据、有范围、结论明确"，而是"用户点了接受" | **高** —— 经验层的准入条件保持可解释、可核对 | 中 |
| 状态管理成本 | 低 | 低（仍只 3 个状态 + 1 条撤销迁移） | 最低 |
| 10 天 V1 可行性 | 高 | 高 | 高 |
| 主要风险 | **口径崩塌**：与 Experience Asset 的定义（D-015）和 E1–E5（D-021）同时冲突；并会诱发"凑经验"动机 | 需明确"撤销"的语义边界（见 §1.3） | 用户在演示中一旦误点接受便无法修正，主链体验断裂 |

### 1.3 单一候选（**推荐方案 B**）

> **候选（`PROPOSED / 需人工确认`）**：**Q12 采用方案 B —— 允许撤销；晋升仍须 E1–E5；用户不能绕过 E1–E4。**

规则化表述：

1. **用户对第 ⑧ 步 `Insight` 可执行的动作共四个**：
   - **接受**（`candidate → accepted`）：**仅当 E1–E4 已满足**时可执行；其作用**等价于 E5**，即"用户显式接受"。
   - **修改**（内容被编辑）：见 **§2 新-2**。
   - **拒绝**（`candidate → rejected`）：用户判定该结论不成立 / 不认同；**拒绝不要求 E1–E4 满足**（用户有权否掉任何 AI 判断）。
   - **撤销接受**（`accepted → candidate`）：见下条。
2. **撤销接受的语义（候选）**：`accepted → candidate`。
   - **回到 `candidate`，不是 `rejected`** —— 撤销表示"我暂时不再把它当作可复用经验"，不表示"我认为这条结论不成立"；后者的正确动作是**拒绝**。
   - 撤销后**必须立即从「经验区 / Experience Asset 视图」中移除**（该视图**任何时刻只呈现当前 `accepted` 的 Insight**）。
   - 撤销**不得**：删除该 Insight、删除其引用的 `Formal Attempt`、修改其内容、改变其来源类型（仍为 `Inference`）。
   - 撤销后该 Insight **必须**按 **D-038** 的三段式呈现方式出现在第 ⑧ 步的位置（**缺什么 / 为什么重要 / 如何补充**），**不得静默消失**、**不得隐藏**。
   - **不得**为撤销引入理由必填、次数上限、冷却期或任何阈值（D-037 三问检验）。
   - 允许对同一条 Insight **反复接受 / 撤销**；每次状态迁移**留事件痕迹**（见 §2.5）。
3. **E1–E4 不得被任何用户动作替代**：
   - 用户**不能**把一条 E1–E4 未满足的 `candidate` 置为 `accepted`；
   - 用户**不能**编辑 E1–E4 的判定结果；
   - **D-021 对 E2 / E3 的硬条件地位不变**：即使 E1 / E4 满足，E2 或 E3 不满足时**仍保持 `candidate`**（与 **D-038** 一致），**用户意愿不能改变这一结果**。
4. **撤销后重新接受**：须**重新检查 E1–E4**（因为内容未变但引用证据可能已变，且检查成本低）；满足则用户可再次接受。

### 1.4 「手动晋升」这一术语的处置（**建议废止**）

> **候选（`PROPOSED / 需人工确认`）**：**"手动晋升"这一术语应予废止**，替换为 ——
> 「**用户可以显式接受一条已满足 E1–E4 的 `Candidate Insight`**」。

理由（三条）：

1. **"手动晋升"在语义上暗示存在一条独立于 E1–E4 的通路** —— 它把"用户接受（E5）"与"满足条件（E1–E4）"混在一句话里，是本会话最容易产生实现歧义的表述。
2. 该术语**天然指向方案 A** —— 只要文档里保留"手动晋升"，实现侧几乎必然做出"用户可绕过 E1–E4"的按钮，从而使 D-021 事实上失效。
3. 正确机制是**两段式的**：**系统检查 E1–E4 → 用户决定 E5**。"手动晋升"把两段压成一段，失去了"条件先成立"这一层。

**配套术语建议（同为候选）**：

| 建议废止 | 建议替代 | 原因 |
|---|---|---|
| 手动晋升 / 强制晋升 / 直接晋升为经验 | **显式接受（E5）** | 避免暗示存在绕过 E1–E4 的通路 |
| 删除经验 / 取消经验资产 | **撤销接受** | "删除"会与 Q31（用户主动删除 / 归档，**本会话不裁决**）混淆 |
| 降级经验 / 经验降级 | **回到候选（`candidate`）** | "降级"暗示存在经验等级，与 D-021"不打分、不设等级"、D-037 禁止清单冲突 |

### 1.5 主要放弃方案

- **方案 A（放弃）**：**与 D-021 直接冲突** —— E1–E4 将不再是硬条件；并使 `Experience Asset` 退化为"用户点过接受的条目"，与 D-015 对 Experience Asset 的实质定义（带明确适用条件与证据来源）脱节。另会诱发"凑经验资产"动机（[R1] 已否定价值排序类取向）。
- **方案 C（放弃）**：**与 D-014 的决策型 `Inference` 规则形成弱冲突** —— 用户在接受后改变主意时，若只能使用 `rejected`，会把"我不再采用"表达成"这条结论不成立"，污染 `rejected` 的语义；同时会造成演示中"误点即不可修正"的主链体验断裂。C 的唯一优点（状态管理更简单）在本项中不构成充分理由。

## 2. 新-2｜`accepted` Insight 被修改后的状态机

### 2.1 问题与既有约束

> **问题**：`accepted` 的 Insight 被用户修改后，状态应如何变化？
> **历史候选（`PROPOSED`，不得直接继承）**：修改后回到 `candidate`、重新检查 E1–E4、再由用户接受。

既有约束：

| 依据 | 约束 |
|---|---|
| **D-021** | E2（结论明确）/ E3（适用范围明确）都是**内容质量条件**；内容变化必然可能使它们从满足变为不满足 |
| **D-014** | `accepted` 后来源仍为 `Inference`；**不得使用"已证实"** |
| **D-015** | 状态集固定为 `candidate` / `accepted` / `rejected`；**不新增状态** |
| **D-038** | 不满足 E2 / E3 时必须"保持 `candidate` + 三段式说明"，**不得自动补字段、不得自动改写、不得自动晋升** |
| **[D9] ⑩** | 假设必须能追溯到历史记录证据 —— 追溯对象是**引用的 `Formal Attempt` 与事实字段**，不是"这条经验的历次措辞" |
| **D-012 / D-021** | 不得为"展示标题"等目的**新增字段** |

### 2.2 方案比较

| 维度 | **方案 A**：修改后仍保持 `accepted` | **方案 B**：任意修改立即退回 `candidate` | **方案 C**：只对"实质性修改"退回 `candidate` |
|---|---|---|---|
| 机制 | 内容可变、状态不变 | 内容任一变化 → 退回 `candidate` → 重检 E1–E4 → 用户重新接受 | 由系统 / 用户判断该次编辑是否"实质性"，只有实质性修改才退回 |
| 与 **D-021** 一致性 | **冲突倾向** —— 可能出现"内容已改到不满足 E2 / E3，状态仍是 `accepted`"，使 `accepted` 不再代表"结论明确 + 范围明确" | **一致** —— 每次内容变化都重新过条件 | **一致**（但判据未定义） |
| 与 **D-038** 一致性 | **冲突** —— E2 / E3 不满足时必须"保持 candidate"，A 下无法保证 | 一致 | 一致 |
| 可判定性 | **高**（取决于"是否发生修改"） | **高**（取决于"是否修改了某个特定字段"） | **低** —— "实质性"无法枚举，只能逐次主观判断 → **必然产生隐性判断** |
| 实现风险 | 低（但正确性风险高） | 低 | **高** —— 判据缺失会导致同类编辑在不同位置得到不同结果，且无法验收 |
| 用户成本 | 最低 | 略高（拼写微调也需重新点接受） | 最低（但代价转移为不可预期的行为） |
| 可信度 | **低** —— 经验层的准入条件可被无声绕过 | **高** | 中（依赖实现者的主观一致） |
| 10 天 V1 可行性 | 高 | 高 | 中（需先定义判据；未定义时不可实现） |

### 2.3 单一候选（**推荐方案 B，并配一条可枚举的字段判据**）

> **候选（`PROPOSED / 需人工确认`）**：**V1 采用简单一致规则 —— `accepted` Insight 的「内容性字段」被修改后，状态退回 `candidate`；随即重新检查 E1–E4；满足 E1–E4 后由用户重新接受（E5）。**

规则化表述：

1. **触发退回**：`accepted` Insight 的**内容性字段**任一被用户编辑 → `accepted → candidate`。
2. **不触发退回**：仅编辑**非语义的展示性 / 元信息**（下条枚举）。
3. **退回后立即**：
   - **重新检查 E1–E4**（同屏完成，成本低）；
   - E1–E4 **全部满足** → 保持 `candidate`，并**显式提示"内容已修改，需要重新接受"**；
   - E1–E4 **任一不满足** → 按 **D-038** 呈现（保持 `candidate` + 「当前还不足以成为可复用经验」+ **缺什么 / 为什么重要 / 如何补充** 三段式）；
   - **何时重新接受由用户决定**，系统**不得**自动接受、**不得**自动补字段、**不得**自动改写结论（D-038）。
4. **退回期间**：该 Insight **立即从「经验区 / Experience Asset 视图」移除**（与 Q12 撤销后同一口径）；**不得删除该 Insight**。
5. **修改不等于拒绝**：修改后的状态是 `candidate`，**不是 `rejected`**。
6. **不得**引入任何"修改幅度 / 修改次数"的计数、评分或阈值（D-037 三问检验）。
7. **不得**为判断修改幅度而**新增字段**（尤其**不得**为了区分"内容"与"标题"而新增独立的"展示标题"字段 —— `accepted Insight` 目前**没有**独立展示标题字段，本项**不因该问题新增字段**）。

### 2.4「内容性字段」判据 —— 用可枚举判据替代"实质性修改"

> **核心（候选）**：**判据不是"这次编辑重不重要"，而是"被编辑的字段是否属于内容性字段集合"。**
> 前者不可判定 → 必然产生隐性判断；后者**可穷举、可枚举、无主观判断**。

| 类别 | 含义 | 修改后的后果 | 说明 |
|---|---|---|---|
| **内容性字段（触发退回）** | ① **经验命题内容**（结论表述）；② **适用范围 / 条件集合**；③ **引用清单**（引用了哪些 `Formal Attempt` / 哪些事实字段）；④ **判断依据 / 可验证判据**（第 ⑦⑧ 项相关内容，D-032 / D-033） | `accepted → candidate` + 重检 E1–E4 | 这四类**正是 E1–E4 的判定输入**：任一类变化都可能使 E1–E4 从满足变为不满足 → 必须重检，因此必须退回 |
| **非语义展示性 / 元信息（不触发退回）** | 例：列表展示顺序、"已读 / 收藏"标记、用户个人备注 | 状态不变 | **仅在系统中确实存在此类字段时才适用**；**不得为适用本条而新增字段**；若某字段的产品角色尚不确定，**一律按"内容性字段"从严处理**（宁可多退一次） |

**关于"拼写 / 措辞微调也会触发退回"的显式取舍（候选）**：这是**有意为之**。

- 代价：用户做一次无意义的错别字修正，也要重新点一次接受；
- 收益：**不存在隐性判断**；不会出现"内容变了但状态没变"的可信度漏洞；
- 结论：**在 V1 的 10 天窗口内，一次多余的点击远比一个无法验收的判据更划算。**

### 2.5 旧 `accepted` 版本的留痕方式（**产品机制判断，不设计数据库**）

> **问题**：修改后，旧的 `accepted` 版本是否保留？

| 方案 | 机制 | 产品代价 | 与既有约束的关系 |
|---|---|---|---|
| **(a) 覆盖旧版本** | 只保留最新内容，旧版本不可见也不留痕 | **无法回答"这条经验被改过吗、改前是什么状态"** —— 与"不得静默状态变更"的精神冲突 | 成本最低，但**丢失状态迁移痕迹** |
| **(b) 保留历史版本** | 可见的版本列表 / 版本对比 / 可回滚 | 引入版本号、版本对比 UI、回滚机制 → 明确的**范围扩展**；与 D-015"Experience Asset 不是独立实体"的取向相悖 | 需扩展范围，10 天窗口内不划算 |
| **(c) 只留事件日志** | 不保留旧内容全文，只记录**事件**（"该 Insight 于 T 被修改、状态由 `accepted` 变为 `candidate`；并于 T′ 被重新接受"） | 用户看不到历史措辞对比 | **与既有约束最一致**：兼容 [D9] ⑩（追溯对象是引用证据，不是历次措辞）、D-015、[D4] |

> **候选（`PROPOSED / 需人工确认`）**：**V1 采用方案 (c) —— 只留事件日志，不保留旧版本全文、不提供版本对比与回滚。**

配套候选规则：

1. 事件日志**至少记录**：状态迁移（`candidate → accepted` / `accepted → candidate` / `candidate → rejected`）、发生时间、**触发原因类别**（用户接受 / 用户撤销 / 内容修改 / 重新接受）；
2. 事件日志**不得**被用作"经验等级""修改次数评分""经验质量排序"的输入（[R1] / D-021"不打分、不设等级"）；
3. **经验区任何时刻只呈现当前 `accepted` 的 Insight**；曾有过的 `accepted` 历史**不构成"仍然有效"的暗示**；
4. **明确不做（V1）**：可见的版本列表、版本对比、版本回滚、版本号选择。

### 2.6 延伸候选（**candidate / rejected 的修改语义**）—— 需人工确认

> **为什么必须一并裁决**：本项授权范围是"`accepted` 被修改后"，但实现时必然遇到"用户修改一条 `candidate` 或 `rejected` 的 Insight 该怎么办"。若不定义，状态机存在**未定义分支**，实现会自行发明规则。

| 起始状态 | 用户修改内容性字段后 | 状态 |
|---|---|---|
| `accepted` | **本项已被授权** | → **`candidate`**（§2.3） |
| `candidate` | **延伸候选（`PROPOSED`）** | **保持 `candidate`**（本就是待定态）；但**必须重新检查 E1–E4 并刷新呈现**（否则用户会看到过期的"E1–E4 满足情况"） |
| `rejected` | **延伸候选（`PROPOSED`）** | → **`candidate`**（原拒绝判断所依据的内容已不存在，**不得沿用旧拒绝**；且**不得**直接变为 `accepted`） |

> 说明：上表**只有第一行为本项授权范围内的正式候选**；第二、三行属**为保持状态机完整而提出的延伸候选**，**需人工确认**，且**不主张新建独立 Decision ID**（建议作为 D-015 / D-021 的子规则随批承载）。

### 2.7 主要放弃方案与影响范围

**主要放弃方案**

- **方案 A（放弃）**：会出现"内容已改到不满足 E2 / E3，状态仍是 `accepted`"——直接违反 D-021（E2 / E3 为硬条件）与 D-038（E2 / E3 不满足必须保持 `candidate`）。
- **方案 C（放弃）**：**"实质性修改"不可枚举 → 必然导致隐性判断**；同一类编辑在界面上不同位置会得到不同结果，且**无法写验收点**。若强行采用，需先定义"实质性"判据 —— 而该判据在 10 天窗口内没有可枚举的形态。
- **保留历史版本（放弃）**：属明确的范围扩展（版本号 / 对比 / 回滚），与 D-015、[D4] 取向相悖。

**影响范围（确认后）**：`docs/04_USER_FLOW.md` §2.5（修改 → 退回候选 → 重检 → 重新接受）、`docs/05_DATA_MODEL.md`（`Insight` 状态迁移、内容性字段集合、事件日志要求）、`docs/06_AI_CAPABILITIES.md`（A4：修改后必须重检，不得自动改写 / 自动晋升）、`docs/08_UI_SPEC.md`（**仅界面约束**：修改后的提示、经验区即时移除、不得出现版本回滚入口）、`docs/09_TEST_PLAN.md`（第四批验收点）。

## 3. 新-7｜`accepted Hypothesis` 是否成为 Experience Asset

> **本会话最关键问题。** 第三批已确认：第 ⑨ 步的 Hypothesis 输出**不是** `Candidate Insight`（D-022 + 第三批对象边界）。
> 因此**不得**简单写成 `accepted Hypothesis → accepted Insight → Experience Asset` —— 除非明确建立转换机制，而这会**新增对象关系**。

### 3.1 语义前提：两者的时间方向相反

| | **Hypothesis**（第 ⑨ 步输出） | **Experience Asset**（`accepted` Insight 视图） |
|---|---|---|
| 命题形态 | "**下一步改变 X，预计会得到 Y**" | "**在条件 C 下，做过 X，观察到 Y**" |
| 时间方向 | **指向未来**（尚未发生） | **指向过去**（已经发生） |
| 支持的证据存在吗 | **不存在** —— 只有未来的一次尝试才能支持 / 反驳它 | **必须已经存在** —— E1 要求 ≥1 条 `Formal Attempt`，E4 要求可指向具体事实字段 |
| grounding 的含义 | "**假设的输入**（问题对象 / 条件 / 指标 / 排除项）来自历史"（D-030 的 G1–G4） | "**结论已被这批历史证据指向**" |
| 用户"接受"的含义 | "**我认可这是一个值得我下一步去验证的方向**" | "**我认可这条经验在当前适用条件下可复用**" |

> **关键差异**：Hypothesis 的 grounding 说的是"**起点来自历史**"；Experience Asset 的准入说的是"**结论已被历史证据覆盖**"。**这两件事不是同一件事** —— 前者可以成立，而后者完全不成立（因为对应的尝试还没做）。

### 3.2 方案比较

| 维度 | **方案 A**：`accepted History-grounded Hypothesis` **直接**成为 Experience Asset | **方案 B**：Hypothesis **永不**成为 Experience Asset；须经新 `Attempt` + 第 ⑧ 步 | **方案 C**：用户可**手动**把 `accepted Hypothesis` 转成 `Candidate Insight` |
|---|---|---|---|
| 是否需要新对象关系 | **需要**（Hypothesis → 经验层） | **不需要** | **需要**（Hypothesis → Insight 的转换通道） |
| 与 **D-015** 一致性 | **冲突倾向** —— 会使 `Experience Asset` 不再等价于 "`accepted` Insight 的产品视图"，实质引入第二类可晋升对象 | **一致** | **冲突倾向** —— 同上（制造出非第 ⑧ 步产出的 "Insight"） |
| 与 **D-021** 一致性 | **冲突** —— E1 要求"Insight 至少关联 ≥1 条 `Formal Attempt`"，而 Hypothesis 的命题**没有任何对应尝试**；E4 也无法指向"支持 / 反驳该命题的事实字段"（尚不存在） | **一致** | **冲突** —— 同 A |
| 与 **D-022** 一致性 | **冲突** —— 出现了"非第 ⑧ 步路径进入经验层"的通道 | **一致** | **冲突** —— 用户手动制造 `Candidate Insight`，等于绕开"只在第 ⑧ 步生成" |
| 与第三批对象边界（§17.5.3）一致性 | **冲突** —— 第三批明确"不定义 `accepted Hypothesis` → Experience Asset"；A 正是建立该关系 | **一致**（把第三批的"未定义"显式定为"不成立"） | 部分（不把 Hypothesis 称 Insight，但建立了转换） |
| 与 **Q12 候选 B**一致性 | **冲突倾向** —— 相当于给"绕过 E1–E4 的晋升"开了一条旁路 | **一致** | **冲突** —— C 即"手动晋升"的变体 |
| 产品语义正确性 | **错误** —— 出现"未来假设直接成为过去经验" | **正确** | 错误（把判定责任转移给用户手工操作） |
| 对经验层的污染 | **高**（未经验证的方向混入"经验"） | **无** | 高 |
| 闭环是否成立 | 名义成立（但闭环里混入了未验证内容） | **成立且干净** | 名义成立（但依赖用户手工搬移） |
| 实现成本 | 低（但正确性代价高） | 低 | 中（需新增转换入口与状态处理） |

### 3.3 单一候选（**推荐方案 B**）

> **候选（`PROPOSED / 需人工确认`）**：**新-7 采用方案 B —— Hypothesis（两种输出）本身永不成为 Experience Asset。**
>
> **它的生命周期止于"用户接受 / 拒绝 + 作为下一步待验证方向"。**
> **只有用户实际执行该方向、产生新的 `Formal Attempt` 之后，该 Attempt 参与 [D9] 第 ⑥⑦⑧ 步，才可能生成新的 `Candidate Insight`，再经 E1–E5 成为 Experience Asset。**

规则化表述：

1. **`History-grounded Hypothesis` 与 `Model Suggestion` 一律不得成为 Experience Asset**，**不得**在 Experience Asset 视图中出现，**不得**被任何"经验"措辞指代。
2. **用户对 Hypothesis 的"接受"** 表示：**"我认可这是一个值得我下一步验证的方向"** ——
   - **不表示**该假设已被支持；
   - **不表示**该假设已成为经验；
   - **不表示**获得了任何历史 grounding 之外的资格。
3. **Hypothesis 的接受 / 拒绝是决策型 `Inference` 的确认动作（D-014）**，来源类型恒为 `Inference`。
   - **本项只使用"接受 / 拒绝"这一层结果**；**不得**为 Hypothesis 建立与 Experience Asset 相关的生命周期状态机；
   - **`Insight` 的 `candidate` / `accepted` / `rejected` 仅适用于第 ⑧ 步产物**，**不得**套用到 Hypothesis 上（第三批已锁定，本项不改变）。
4. **正确的转化路径（唯一）**：
   ```
   History-grounded Hypothesis（未来待验证方向）
        ↓ 用户实际执行该方向
   新的 Formal Attempt（结果可为 Failed / Partial / Success / Unknown，均合法）
        ↓ 第 ⑥⑦ 步（与相关历史比较）
   第 ⑧ 步 → 新的 Candidate Insight
        ↓ E1–E5
   Experience Asset（可能新增一条经验，也可能修正 / 冲突于既有经验）
   ```
5. **不得**以"用户接受 Hypothesis"替代上述路径中的任何一环；**不得**在 UI 或文案中把已接受的 Hypothesis 呈现为"经验 / 结论 / 已确认"。
6. **Hypothesis 不承担 grounding、不计入 `N_检索` / `N_引用`** —— 它是 `Inference`；与 D-030 / M-11 对"`accepted Insight` 即使已接受也不能承担 grounding"的处置同源，**属延伸，不属新增规则**。

### 3.4 闭环评估（**本项的核心价值**）

```
        ┌───────────────────────────────────────────────┐
        │                                               │
        ▼                                               │
  Experience Asset                                      │
  （= accepted Insight 的产品视图）                       │
        │                                               │
        │ ① 作为【推理输入】参与第 ⑨ 步                │
        │   （不可承担 grounding，不计入 N_引用）        │
        ▼                                               │
  History-grounded Hypothesis                           │
  （未来待验证方向；用户可接受 / 拒绝）                    │
        │                                               │
        │ ② 用户实际执行                                │
        ▼                                               │
  新的 Formal Attempt ── ③ 第 ⑥⑦ 步与历史比较           │
  （Failed / Partial / Success / Unknown）              │
        │                                               │
        │ ④ 第 ⑧ 步生成 Candidate Insight              │
        ▼                                               │
  新的 Candidate Insight ── ⑤ E1–E5 ────────────────────┘
```

**评估结论（候选）**：

| 评估项 | 结论 |
|---|---|
| 是否形成闭环 | **是** —— `经验 → 方向 → 新记录 → 新经验` 自我增强闭环成立，且**每一环都有明确的证据锚定** |
| 是否为产品差异化 | **是** —— 本闭环同时做到两件通常互斥的事：① 让历史失败**真实参与**下一步方向推理；② **不允许**未经验证的未来假设污染过去经验 |
| 是否会污染经验资产 | **不会** —— 经验层的准入条件保持为"**证据已经存在**"（E1 / E4），而不是"用户觉得有道理" |
| 是否引入"未来假设直接成为过去经验"的逻辑错误 | **不会** |
| 是否新增对象关系 | **不新增**（Hypothesis 与 Experience Asset 之间**不存在**直接关系） |
| 与 D-022 / Q12 候选 B 的关系 | **互相强化** —— D-022 保证 `Candidate Insight` 只有一个来源；Q12 候选 B 保证 E1–E4 不可绕过；本项保证 Hypothesis 不构成第三条通路 |

### 3.5 为什么 A / C 会破坏已确认边界（逐条）

- **方案 A 破坏 D-021（最直接）**：E1 的原文是"Insight 至少关联 ≥ 1 条 `Formal Attempt`"。Hypothesis 所对应的"尝试"**尚未发生**；若把 `accepted Hypothesis` 视为经验，E1 在该条经验上**无对应物**，E1 事实上被架空。E4 同理 —— 它要求指向"**支持 / 反驳该命题的**事实字段"，而这类字段在假设阶段不存在。
- **方案 A 破坏 D-015**：`Experience Asset` 会被实质扩展为"`accepted` Insight **或** `accepted Hypothesis`"，即引入第二类可晋升对象；这与 D-015"`Experience Asset` 不是第三个独立事实对象，而是 `accepted` Insight 的产品视图"的等价关系冲突。
- **方案 A 破坏第三批对象边界**：第三批正是为了修复"第 ⑨ 步产物被误当 `Candidate Insight`"而建立边界（§17.5.3）；A 会在**经验层**重新制造同一个混淆。
- **方案 C 破坏 D-022**：C 允许用户手工制造一条 `Candidate Insight`，而 D-022 明确 `Candidate Insight` **只在第 ⑧ 步生成**、**不做 candidate 待办池 / 不做其他生成通道**。C 且其 E1 / E4 无法成立（没有任何验证它的 `Formal Attempt`）。
- **方案 C 与 Q12 候选 B 冲突**：C 本质是"手动晋升"的变体 —— 用户通过两次点击（转成 Insight → 接受）即可让一条无验证证据的内容进入经验层，等于绕开 E1–E4。

### 3.6 主要放弃方案与影响范围

**主要放弃方案**：方案 A（未来假设直接成为过去经验，架空 E1 / E4、破坏 D-015 与第三批对象边界）、方案 C（用户手动转换，绕开 E1–E4 与 D-022；且转换后 E1 / E4 仍无法成立）。

## 4. 新-10｜`Model Suggestion` 保存后的性质与晋升资格

### 4.1 问题与既有约束

> **问题**：用户对 `Model Suggestion` 选择"保存"之后，它是什么？能否经"接受"成为 Experience Asset？

第三批已确认（**不重开**）：

| 依据 | 约束 |
|---|---|
| 第三批对象边界（D-027 / D-030 / §17.5.3） | `Model Suggestion` **非历史经验依据**；**不是 `Candidate Insight`**；**不计入** [D9] ⑨⑩；**不得升级**为 `History-grounded Hypothesis` |
| **D-029 / D-034** | `N_检索 = 0` 时允许**可选** `Model Suggestion`（用户可选择生成 / 跳过）；**系统不得默认以它填充第 ⑨ 步位置** |
| **D-030** | 无真实 grounding → **整体只能为 `Model Suggestion`**；**只有 `Fact` 引用可承担 grounding** |
| **D-021** | E1（≥1 条 `Formal Attempt`）/ E4（证据可追溯）为硬条件 |
| **D-014** | 决策型 `Inference` 必须显式接受 / 拒绝；接受后来源仍为 `Inference` |

### 4.2 必须区分的四个动作（**本项的核心**）

> **候选（`PROPOSED / 需人工确认`）**：以下四件事**在产品语义上互不等价**，**不得互相替代、不得互相暗示**：

| # | 动作 | 它表示什么 | 它**不**表示 |
|---|---|---|---|
| 1 | **保存**（`Model Suggestion`） | "我想把这条**模型建议**留在**本次记录**里，以便之后回看" | 不表示接受为事实；不表示成为经验；不表示获得历史 grounding；**不属于决策型 `Inference` 的接受动作**（D-014） |
| 2 | **接受为事实** | **不存在这个动作** —— 任何 `Inference` 都不得升级为 `Fact`（D-007 / D-014 / D-015） | —— |
| 3 | **成为经验资产** | **不成立** —— 需经 E1–E5 | —— |
| 4 | **获得历史 grounding** | **永不成立** —— `Model Suggestion` 无历史锚点，**不得**因保存 / 接受而取得 | —— |

### 4.3 方案比较

| 维度 | **方案 A**：可保存为持久化 Suggestion，标记恒存，永不直接晋升 | **方案 B**：保存后可 `accepted` 并成为 Experience Asset | **方案 C**：V1 不允许保存 |
|---|---|---|---|
| 与 **D-021** 一致性 | **一致** | **冲突** —— E1 无对应 `Formal Attempt`，E4 无事实字段可指 | 一致 |
| 与 **D-030** 一致性 | **一致** | **冲突** —— 无 grounding 的内容进入经验层 | 一致 |

| 第三批对象边界（§17.5.3） | **一致** | **冲突** —— 使 `Model Suggestion` 事实上取得与 History-grounded 同等的资产地位 | 一致 |
| 与 **Q12 候选 B / 新-7 候选 B** 一致性 | **一致**（同一原则：无历史锚定不得进入经验层） | 冲突 | 一致 |
| 用户价值 | **高** —— 冷启动用户也能留下这次的建议，并在本次记录中回看 | 高（但代价是经验层失真） | 低（看到即失去） |

### 4.4 单一候选（**推荐方案 A**）

> **候选（`PROPOSED / 需人工确认`）**：**新-10 采用方案 A。**
>
> **允许保存；保存后成为一条持久化的 `Model Suggestion`（来源类型恒为 `Inference`），始终保留「非历史经验依据」标记，永不直接晋升为 Experience Asset，也永不获得历史 grounding。**

规则化表述：

1. **保存后它仍然是 `Model Suggestion`** —— 名称与性质**都不因保存而改变**；**不得**改称"经验 / 候选经验 / Insight / Hypothesis"。
2. **「非你的历史经验依据」标记恒存** —— 与是否保存、是否被用户标记为"打算采用"无关；**整体显著标注**（第三批 H2–H4 / D-036），**不是小标签**。
3. **不得进入 Experience Asset 视图**；**不得**与经验资产混列。
4. **不计入 `N_检索` / `N_引用`**；**不承担 grounding**；**不得**被 [D9] ⑩ 追溯为历史证据（与 D-030 / M-11 同源）。
5. **不得**因保存而取得 `History-grounded Hypothesis` 地位（第三批已锁定：**不得升级**）。
6. **保存 ≠ 决策型 `Inference` 的接受动作**（D-014）：保存**不改变任何持久化的业务判断状态**，因此**不需要**接受 / 拒绝的确认流程；**不得**把"保存"渲染为"接受 / 确认 / 采纳"。
7. **V1 的范围约束（候选）**：保存后的 `Model Suggestion` **仅属于本次主链记录的第 ⑨ 步输出并被持久化，可在本次记录中回看**；**V1 不建立跨记录的建议库 / 建议列表 / 建议待办视图**（避免形成与 D-022 所反对的"候选待办池"形态相近的模块）。
8. **不得**在界面上使用"保存为经验 / 保存为资产 / 采纳为经验"等表达（D-036 "只锁语义要求 + 禁止清单"）。

### 4.5 用户未来真的采用时的**正确路径**

```
Model Suggestion（非历史经验依据）
     ↓ 用户实施该方向
新的 Formal Attempt（进入正式历史，可承担 grounding）
     ↓ 第 ⑥⑦ 步 + 第 ⑧ 步
新的 Candidate Insight
     ↓ E1–E5
Experience Asset
```

**错误路径（必须显式排除）**：

```
Model Suggestion  →（点击接受）→ Experience Asset        ❌
```

> **关键说明（候选）**：即使用户未来**真的采用了**某条 `Model Suggestion`，最终形成的 Experience Asset 的**证据来源是"那次执行产生的 `Formal Attempt`"**，**与"那条 `Model Suggestion` 本身"无关** ——
> **`Model Suggestion` 永远不构成经验层的证据来源。**
> 这与 **D-030 / M-11**（"`accepted Insight` 即使已被接受也不能承担 grounding"）是**同一条原则的延伸**：**能否承担 grounding 取决于"是否为可追溯的 `Fact` 引用"，而不取决于"用户是否接受过它"。**

**延伸候选（`PROPOSED / 需人工确认`）**：保存后的 `Model Suggestion` 若在后续第 ⑨ 步被引用，**只能作【模型先验】分区的推理输入**，须单独标注、**不计入 `N_引用`**、**不得成为唯一依据**。

### 4.6 主要放弃方案与影响范围

**主要放弃方案**

- **方案 B（放弃）**：**与 D-021（E1 / E4）和 D-030（grounding）同时冲突**；并使第三批专门建立的对象边界（§17.5.3）在资产层失效 —— 无历史锚定的内容将取得与 `History-grounded Hypothesis` 同等的资产地位。
- **方案 C（放弃）**：不违反任何已确认决策，属**可裁决项**；但其代价是"**用户看得到却留不下**"的体验断裂，且会把用户推向在产品之外保存内容（记录散落），与 [D4] / 长期价值取向相悖。C 唯一真正规避的风险是"用户把保存误读为已确认"——**该风险由方案 A 的第 2 / 6 / 8 条（整体标注 + 不得使用接受类措辞 + 独立区域）兜住**，无需通过禁止保存来规避。

**影响范围（确认后）**：`docs/03_V1_SCOPE.md`（`Model Suggestion` 可保存但不可晋升；不做跨记录建议库）、`docs/04_USER_FLOW.md` §2.6 / §3、`docs/05_DATA_MODEL.md`（保存后的性质、标记恒存、不承担 grounding、不计入 `N`、与经验层无关系）、`docs/06_AI_CAPABILITIES.md`（A5 与红线：不得称经验、不得因保存升级）、`docs/08_UI_SPEC.md`（**仅界面约束**：独立区域、整体标注、"保存"不得渲染为"接受"）、`docs/09_TEST_PLAN.md`（第四批验收点）。
