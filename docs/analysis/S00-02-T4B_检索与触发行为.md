## 1. Q29｜`Formal Attempt` 保存后是否自动触发第 ⑥ 步检索

### 1.1 问题重述与既有依据

**问题**：第 ⑤ 步"用户确认后保存"完成之后，第 ⑥ 步"系统检索相关历史 Attempt"**由谁触发**、**何时触发**？

| 既有依据 | 内容 | 对 Q29 的约束 |
|---|---|---|
| **[D9] 第 ⑤ / ⑥ 步** | ⑤ 用户确认后保存 → ⑥ **系统**能够检索相关历史 Attempt | ⑥ 的**主体是"系统"**（不是"用户"）；⑤⑥ **同属 P0 验收主链**，任一环节无法完成即 V1 未完成 |
| **[D9] 链式验收** | 十步是**唯一验收口径**；⑥→⑦→⑧→⑨→⑩ 必须能**连续走通** | 任何**未在 D9 中列出的用户动作**若成为 ⑥ 的前置，都会改变验收路径的性质 |
| **[D4] 即时价值** | 用户当下要的是"**理解刚刚发生的失败，并找到下一步值得验证的方向**" | 历史对照是**即时价值的一部分**，不是可选增值 |
| **[D7] / [R6]** | 跨记录参与下一轮推理是本产品的核心差异化 | 若历史对照变为"用户主动索取才出现"，差异化变为 opt-in |
| **D-012** | `Draft` **不进入正式历史比较**；**只有 `Formal Attempt` 才能进入第 ⑥ 步及之后** | 触发条件必须以 `Formal Attempt` 为前提 |
| **D-022** | `Candidate Insight` **只在第 ⑧ 步生成**；V1 **不做**后台自动生成 / 保存后自动生成 / 异步批量 / 定期挖掘 / `candidate` 待办池 | **必须显式说明本候选不触碰该条** → §1.4 G-2 |
| **主文档 §8.5** | 第 ⑤ 步"进入下一步条件 = **保存成功**"；失败 → 保留草稿并显式提示 | 触发条件与"保存成功"绑定 |
| **主文档 §8.6** | 第 ⑥ 步"用户输入：**无（自动触发）**；可选调整范围（同 Project / 全部）" | 首轮候选**已是自动触发**，但该 §8 属 `PROPOSED` 设计稿，**未经人工确认** |
| **T4-C §2.5 ⑥ 行** | ⑥ 的 step-gate：正常通过 = 检索执行完成（含 `N_检索 = 0`）；**阻断 = 无**；检索失败 → 提示可重试、**不设次数门槛**、**不得虚构相似记录** | 本文**引用**，不重复裁决 |

### 1.2 三方案比较

| 方案 | 机制 | 主要优点 | 主要风险 / 否决理由 |
|---|---|---|---|
| **A｜保存成功后自动触发** | `Formal Attempt` 保存成功 → **系统立即执行第 ⑥ 步检索** | ① **与 D9 的字面与精神一致**：⑥ 的主体是"**系统**能够检索"，无需用户发起；② **⑤→⑥ 无缝衔接**，不插入未定义的主链动作；③ 与 [D4] 即时价值一致（用户"刚记录完"的那一刻正是最关心"以前有没有类似情况"的时刻）；④ 与 [R6] 一致（跨记录参与推理是**默认路径**而非 opt-in）；⑤ 与 D-034 / D-036 已定义的**空态机制天然兼容** —— `N_检索 = 0` 早有合法的诚实降级出口，自动触发**不会**产生"检索不到就出错"的风险 | 需明确**触发条件与边界**（Draft / 保存失败 / 编辑 / 重复保存 / 修改后），否则实现层会自行发明条件 → **本文 §1.4 逐条收口** |
| **B｜保存后用户手动点击「查找相关历史」** | 保存完成 → 停在提示态 → 用户点击后才检索 | 用户完全掌控"是否立刻看历史" | ① **在 D9 的 ⑤ 与 ⑥ 之间插入一个未定义的主链动作** —— D9 十步中**不存在**"用户发起检索"这一环节，若以它作为 ⑥ 的前置，等于**修改主链的验收路径**，而十步结构属已锁定范围（T4-C §1.3 亦明确"不建议增删任何环节"）；② **⑥ 由"系统能力"退化为"用户动作的后果"** —— 用户不点击则 ⑥⑦⑧⑨⑩ **全部不发生**，D9"任一环节无法正常完成即 V1 未完成"的验收将取决于**用户是否知道要点击**，验收不确定；③ **与 [D4] 冲突**：即时价值（找到下一步方向）被放在一次额外点击之后；④ **与 [R6] 冲突**：核心差异化能力变为**需要用户主动索取**；⑤ 检索是**只读、非破坏性**动作，让用户"授权"它没有对应的隐私或风险收益 |
| **C｜自动轻量检索，进入详细比较需用户点击** | 自动跑一次"轻量"检索（给出概览），详细比较页需点击进入 | 折中：既自动，又不一次性压上全部信息 | ① **风险点位移而非消除**：点击位置从 ⑤⑥ 之间移到 **⑥⑦ 之间**，而 **⑦"展示相似点与差异点"本身就是 D9 的主链环节** —— 把 ⑦ 置于点击之后，等于让主链环节**默认不发生**，与 D9 相冲突；② **"轻量检索"与"详细检索"的边界未定义**：在**不得显示数字相似度（D-020）**、**不得设内部隐藏式加权门槛（D-037）**的前提下，无法给"轻量 vs 详细"一个可解释的判据，必然落回"某个内部阈值"，属 **D-037 明令禁止的隐性门槛**；③ **"轻量结果"极易变成证据数量暗示**：一旦呈现"找到 N 条相关"，该数字既非 `N_检索` 档位、亦非 `N_引用`，**落入 D-037 三类合法数字之外**，会被读成可信度信号；④ **其动机已被 Q14 覆盖**：C 想要的"不一次性压上太多信息"，正是 **Q14 的"首屏主对照默认 3 条 + 可就地展开"**所解决的问题，且 Q14 方案**不引入任何未定义状态**（§2）；⑤ 引入"已检索但未展示"的中间态，使第 ⑥ 步的完成判定与 ⑦ 的展示判定分离，与 T4-C step-gate 的"⑥ 完成 = 检索执行完成"口径产生第二个版本 |

### 1.3 Q29 单一候选

> **采用方案 A：`Formal Attempt` 保存成功 → 自动触发第 ⑥ 步检索。**
>
> 1. **唯一触发条件** = **一次 `Formal Attempt` 的保存动作成功完成**（即主链第 ⑤ 步的"通过"）。
> 2. **第 ⑥ 步检索不设"用户发起"前置** —— **在 ⑤ 与 ⑥ 之间不得插入任何未在 D9 中列出的用户动作**（不设"查找相关历史"按钮作为必经入口）。
> 3. **不采纳方案 C** —— **不设"轻量检索 / 详细比较"两级检索**；"信息不宜一次性铺满"由 **Q14 的首屏展示规则**解决，**不通过点击门控第七步**。
> 4. **自动触发的对象与范围**：只对**刚保存成功的那条 `Formal Attempt`** 触发一次；**不触发**任何后台、异步、批量、定时任务。
> 5. **自动触发不改变第 ⑧ 步的生成时机** —— 第 ⑧ 步 `Candidate Insight` **仍在第 ⑧ 步生成**，**不因自动触发而提前到保存时刻**（符合 D-022）。
> 6. **触发行为与"数据来源"字段无关**（现场记录 / 事后补录 / Demo 示例数据**同等触发**）—— **不得以来源字段作为能力门控**（沿用 D-034 对「数据来源」字段的使用边界）。**补录场景下的主链适用性另有边界问题 → 新-T4B-4**。

**放弃的方案**：B（在 ⑤⑥ 之间插入未定义主链环节 + 使 ⑥ 由系统能力退化为用户动作的后果 + 与 [D4] / [R6] 冲突）；C（把点击门位移到 ⑥⑦ 之间、使 ⑦ 默认不发生 + "轻量 / 详细"边界在 D-020 / D-037 约束下**无法定义** + 其动机已被 Q14 覆盖）。

### 1.4 触发条件子规则（Q29 核心，T-1 – T-7）

| 编号 | 规则 | 依据 / 说明 |
|---|---|---|
| **T-1** | **触发 = 事件驱动，不是状态驱动**：触发源是"**一次保存动作成功**"这一**事件**，不是"该记录是否已检索过"这一**状态**。**不得**实现为"打开记录时若未检索过则检索" | 避免引入"已检索过"这一状态标记（→ §1.6）；也避免"同一动作触发多次 / 不同入口触发结果不一致" |
| **T-2** | **`Draft` 不触发**：保存 `Draft`（第 ① 步产生原始输入即暂存）**不触发**第 ⑥ 步检索 | **D-012**：`Draft` 不进入正式历史比较、不参与正式 E4 历史孵化 |
| **T-3** | **保存失败不触发**：第 ⑤ 步保存**未成功**时**不触发**；后果按 §8.5 处理（保留草稿 + 显式提示 + 可重试） | 主文档 §8.5"进入下一步条件 = 保存成功"；**不得**在未落库的情况下以其为输入做检索（否则 ⑩ 追溯会指向不存在的记录） |
| **T-4** | **仅编辑 `Draft` 不触发**：解析 / 追问 / 修改草稿 / 中途离开 / 再次续写**均不触发**；`Draft` 阶段的所有用户动作都**不是**触发事件 | 与 T-2 同源；且与 D-018（M2 阶段**固定禁止**历史对照类追问）在语义上一致 —— **录入阶段不涉历史比较** |
| **T-5** | **重复保存不重复触发（幂等）**：同一次保存流程内重复触发保存（重复点击 / 网络重试）**只产生一次检索**；**不得**因重复提交而重复检索、重复刷新结果 | 幂等性是"不得虚构 / 不得重复制造对照集合"的最低要求；**该幂等处属实现层，不构成产品层门槛、不计入任何次数统计** |
| **T-6** | **修改 `Formal Attempt` 不自动重跑检索**：保存后的任何字段修改（含**影响 Level A 的字段**：目标 / 实际尝试·方案·技术对象 / 条件 / 结果·现象）**不自动重新触发检索** | 理由见 §1.5（三条） |
| **T-7** | **修改后必须"显式提示 + 提供显式重跑入口"**：系统应显式提示「**该记录已被修改，先前的历史比较结果可能不再适用**」，并提供**由用户显式发起的「重新检索」**；**不得静默沿用旧结果**，**也不得自动重新生成第 ⑧ / ⑨ 步产物** | 与 D-036「不得静默」同源；与 D-022 / T4-A 新-2（内容性字段修改 → 退回 `candidate`）**同向**，但**本文不裁决状态退回** → §1.7 归口 |

### 1.5 为什么"修改后不自动重跑"（T-6 的三条理由）

| # | 理由 |
|---|---|
| **① 主链定义在"保存路径"上，不在"编辑路径"上** | D9 的 ⑤→⑥ 描述的是**一次记录的形成过程**。事后编辑是**对既有对象的维护动作**，不是主链的一次重放。若把"每次编辑"都升级为主链重跑，等于把**编辑动作**也纳入 D9 验收路径，属**扩张主链**。 |
| **② 编辑过程是不稳定态，自动重跑会产生不确定的中间结果** | 用户在编辑时字段是**逐步变化**的（先改目标、再改条件）。若每次变更都自动重跑，检索会在**半完成状态**下反复执行，产生的对照集合既不可解释，**也会与"何时算一次检索完成"产生冲突**（第 ⑥ 步的完成判定会失去唯一定义）。 |
| **③ 自动重跑会连带强制重生成下游产物，与 D-022 / 新-2 直接冲撞** | 若修改即自动重跑 ⑥，那么 ⑦ 的对照、⑧ 的 `Candidate Insight`、⑨ 的 Hypothesis **在逻辑上全部失去依据**。此时实现层只有两个选择：**自动重生成下游产物**（= 绕过用户在场与 E5 显式接受，违反 D-022 / D-021）或**保留旧产物但不说明**（= 静默，违反 D-036）。**两条都不可接受**，因此正确做法是：**不自动重跑 + 显式提示 + 由用户显式发起**。 |

> **对称性说明（防止被质疑"保存自动、修改手动"不一致）**：两者的**性质不同** —— 保存是**主链规定动作**（D9 的 ⑤），修改是**主链之外的对象维护**。规则并非"自动 vs 手动"随意二分，而是：**主链规定动作 → 自动**；**主链外动作 → 不自动改变主链结果，但必须提示 + 允许用户显式重放**。该原则与 T4-C 的"**门槛 ≠ 阻断**、**不升级 ≠ 丢弃**"属同一类"动作与后果必须可分辨"的取向。

### 1.6 与 Q04 的接口：**是否需要"已检索过"的系统元数据**（T4-C 明确交本文）

> T4-C §8.1 原文：「**Q04 × Q29**：第 ⑥ 步检索的触发时机（其他责任范围）。**系统元数据是否用于判定'是否已检索过'属 Q29** → 本文不涉及。」

**本文回答**：

| 结论 | 内容 | 依据 |

## 2. Q14｜相关历史返回条数

### 2.1 先做一次口径分离（**本项最容易出错之处**）

> 任务的明确要求：**"返回 / 检索多少" ≠ "首屏主对照展示多少"**；**不得把 UI 阅读负荷参数误写成检索算法限制**。

| 层面 | 含义 | 由谁决定 | 允许出现数字吗 |
|---|---|---|---|
| **① 检索层** | 第 ⑥ 步实际判定为"相关（Level A 命中）且可被引用"的记录**集合大小** = **`N_检索`** | **产品机制**（D-035） | **是 —— 但只以"结构档位 0 / 1 / ≥2"形式使用，不得作为"检索上限"** |
| **② 展示层** | 第 ⑦ 步**首屏一次性呈现**的对照对象数量 | **阅读负荷控制**（Q14 本文） | **是 —— 属 D-037 三类合法数字之第 ③ 类** |
| **③ 引用层** | 真正参与第 ⑨ 步 Hypothesis 的证据数量 = **`N_引用`** | **产品机制**（D-035 / D-030） | **是 —— 且是唯一被允许作为"证据条数"呈现的数字**（D-037「始终展示 `N_引用`」） |

> **核心红线**：**② 的数字不得反向约束 ①，也不得反向约束 ③**。否则"阅读负荷参数"就变成了"证据门槛"，直接违反 D-037 的三问检验（**Q-3：该数字是否绑定输出内容量** —— 若展示上限决定了能引用多少证据，Q-3 即为"是"，该数字立即不合法）。

### 2.2 四方案比较

| 方案 | 机制 | 主要优点 | 主要风险 / 否决理由 |
|---|---|---|---|
| **A｜固定主 3，硬上限 10** | 首屏固定 3 条；展开后最多 10 条；两项均为**产品层硬约束** | 数值明确、实现简单 | ① **"主 3"被固定化后会产生"补满"压力** —— 当实际相关只有 1 条时，"固定 3"会诱导补入 Level B-only 的记录（**违反 D-019 / AC-20**）；② **"上限 10"缺少产品依据**：展开是**用户主动表达"我还要看"**的动作，此时再设硬上限，**既不是防认知负荷（用户已主动要看），也可能阻止用户查看被 ⑧⑨ 引用的证据**；③ 一旦写入 S00-02，**该数字会被实现为产品承诺**，后续要改需走决策变更流程，而它本质是 **UI / 实现参数** |
| **B｜主 3，可继续展开，不锁死绝对总上限**（+ 不足则展示实际数量） | 首屏**默认 3 条**；**不足则如实展示实际数量**；**可就地展开查看更多**；**不在本阶段锁死"绝对上限"** | ① 完全落在 **D-037 第 ③ 类合法数字（阅读负荷控制）**内；② 不产生"补满"压力；③ 展开由用户主导，**不会阻止查看被引用的证据**；④ **不把 UI 参数提升为产品机制** | 无明显风险；**需配套三条护栏**：**不得补满**、**折叠 ≠ 排除**、**展示条数不得成为证据门槛**（§2.5） |
| **C｜主结果自适应 1–3，其余按需展开** | 首屏数量在 1–3 之间"自适应" | 看起来更"聪明"、信息密度可变 | ① **"自适应"缺少可解释判据**：在**禁止数字相似度（D-020）**、**禁止内部隐藏式加权门槛（D-037）**的前提下，系统凭什么决定这次显示 1 条、下次显示 3 条？必然落回某个**内部分值 / 阈值** → **命中 D-037 明令禁止的"内部打分但用户不可见的门槛"**；② 用户无法解释"为什么这次只有 1 条"，会读成**质量信号**（"这次相关记录少，说明我的记录没价值"）→ 违背 D-035「档位不是可信度等级」；③ **其合理内核已被 B 吸收** —— C 真正想表达的"不足时不要硬凑 3 条"，在 B 中即"**不足则展示实际数量**"。因此 **C 不单独成立，其内核并入 B，其"按强度自适应"读法被明确否决** |
| **D｜一次返回全部** | 检索结果一次性全部呈现 | 不遗漏任何相关记录 | ① **首屏认知负荷不可控**：第 ⑦ 步需要**逐条比较**相似点与差异点，条数无上限时对照区不可读（10 天 V1 的可用性底线）；② **与 D-037 第 ③ 类的存在理由直接冲突** —— 该类数字之所以合法，正是因为**必须控制阅读负荷**；若取消控制，等于放弃唯一被允许的展示层数字；③ **不构成"更完整"**：遗漏是可以避免的（展开即可达），而"一次铺满"带来的后果不可逆（用户不再阅读）。**D 的诉求"不得遗漏"由 B 的"展开可达 + 折叠 ≠ 排除"满足** |

### 2.3 Q14 单一候选

> **采用方案 B（并吸收方案 C 的合理内核）。**
>
> 1. **首屏主对照默认呈现 3 条**（= D-037 第 ③ 类「阅读负荷控制」的默认初始量）。
> 2. **若实际"相关且可引用"的记录不足 3 条 → 如实展示实际数量**；**1 条就展示 1 条，0 条进入合法空态**。
> 3. **绝不为了凑满 3 条而纳入相关性不足的记录**（**不得**用 Level B 单独成立的记录补位，**不得**用"最近一次"补位）。
> 4. **可就地展开查看更多**；**展开必须可达**（不遗漏）。
> 5. **V1 不在 S00-02 锁死"展开绝对上限 = 10"** —— 该数字**降级为 `08_UI_SPEC.md` / 实现层的呈现参数**（分页、继续加载、滚动等均可），**不作为产品机制约束**。
> 6. **"检索"本身不设条数上限**：所有 Level A 命中且可被引用的记录**均属 `N_检索` 集合**，**不得因首屏展示 3 条而截断 `N_检索`**。

**放弃的方案**：A（"固定 3"制造补满压力 + "上限 10"缺产品依据且可能挡住被引用的证据 + 把 UI 参数提升为产品机制）；C（"按强度自适应"需要内部判据 → D-020 / D-037；其合理内核并入 B）；D（首屏认知负荷不可控 + 取消唯一的合法展示层数字；其"不遗漏"诉求由 B 的展开可达满足）。

### 2.7 为什么"锁 3"而"不锁 10"（**非对称处理的理由**）

| | 首屏默认量「3」 | 展开上限「10」 |
|---|---|---|
| **作用对象** | **用户第一眼要读几条** —— 必须有一个**具体默认值**，否则界面无法实现（"自适应"在 D-020 / D-037 约束下**没有可解释判据**，见 §2.2 C） | **用户主动要求"继续看"之后**还能看多少 —— 此时用户的阅读意愿已明确表达 |
| **缺失后果** | 无默认值 → 界面无法决定初始呈现，必然由实现层自造数字（**更糟**：数字进了实现层，产品层反而失控） | 无上限 → 只是分页 / 继续加载的形态问题，**不产生机制歧义** |
| **是否有产品依据** | 有：**阅读负荷控制的默认初始量**（D-037 第 ③ 类，明确列的例就是"主对照 3 条"） | **弱**：它只在"用户要看更多"时生效，**此时限制阅读量既无负荷依据，也可能挡住被引用的证据**（V-5 的对照面） |
| **是否可能被读成证据门槛** | **可能** → 用 **V-2 / V-5 / V-6** 三条护栏封住 | **更容易被读成证据门槛**（"最多只有 10 条证据"）→ **不锁它，也就没有这个风险** |
| **本项结论** | ✅ **锁「默认 3 条」** | ❌ **不锁「上限 10」**，留 `08_UI_SPEC.md` |
