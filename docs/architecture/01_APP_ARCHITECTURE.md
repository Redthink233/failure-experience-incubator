## §1 架构必须满足的既有约束（不自创约束，只做技术翻译）

> 以下每条均可回溯到 canonical 或契约，**架构不得以"技术更优雅"为由绕过**。

| 约束组 | 关键约束 | 对架构的直接后果 |
|---|---|---|
| **交付形态** | `TC-78` 浏览器可访问的 Web 应用；在线 Demo **不依赖本机数据库** | 必须云端部署 + 云端持久化 |
| **持久化** | `TC-79` 刷新 / 重启不丢数据 | 必须有托管数据库（浏览器本地存储无法满足"不依赖参赛电脑"） |
| **业务规则不可绕过** | `TC-77` 不得提供绕过 `E1`–`E4` 的晋升路径；`TC-13` 决策型 `Inference` 复用门禁；`TC-57` / `TC-23` 归档与 `Draft` 过滤必须**在所有查询路径**生效 | **规则必须由服务端独占执行**；不得把门槛判定下放到浏览器 |
| **无运行时后台** | `TC-21` ⑤→⑥ 为**同步、幂等**；`BLK-01` Cloud Worker ≠ 运行时后台 Worker；`TC-25` / `TC-26` 不产生后台 / 异步 / 批量 / 定时任务 | **不得**引入队列、定时任务、后台 Worker、异步批处理；⑥ 必须在保存请求的调用链内同步完成 |
| **技术选型排除项** | `R3` 不绑图数据库；`R6` 不以向量数据库等炫技替代产品价值；阶段约束：**不引入独立 Vector DB / Redis / Graph DB** | 依赖清单已排除三类中间件；缓存不得依赖外部缓存服务 |
| **零数值相似度** | `TC-41` 不得计算/存储/传输/展示任何数值化相似度；**内部检索分数不得出现在任何接口响应或界面** | **传输契约不得含 score / confidence / rank 类字段**（需契约测试断言其不存在） |
| **技术层隔离** | `TC-71` `model` / `prompt` / `token` / `temperature` / `trace id` / `latency` / `retries` / 内部检索分数**可存在于技术层，但物理或逻辑隔离 + 不出界面 + 不进 ⑩ 追溯 + 不参与判定** | **不得进入主业务响应体**；独立通道或仅服务端日志 |
| **L4 恰 4 项** | `TC-69` 产品层系统自动记录 = 创建时间 / 最近修改时间 / 数据来源性质 / AI 内容来源标记 | 对外元数据面**恰好 4 项**，不多不少 |
| **来源与角色恒存** | `TC-10`–`TC-12` 每条内容条目必带 `source_type`（`Inference` 另带 `confirmation_class` / `decision_state`）；`TC-45` 每条引用必带 `role` | **内容条目与引用为一等传输对象**，不得压平为裸字段 |
| **检索范围** | `TC-84` 默认全部历史；`Project` **不得**作为准入过滤条件 | 数据访问层**不得**以 `project_id` 做准入过滤 |
| **三层语义分离** | `TC-28` / `TC-61` `GATE` / `RUNTIME` / `ACCEPTANCE` 必须分开；`TC-65` `EXIT-A/B/C` 必须分别建模；契约 §10.2 禁止裸用 `A`/`B`/`C` | 传输层必须能区分"对象门槛未满足 / 技术失败 / 验收"，**且三类出口可区分** |
| **两种空态** | `TC-66` 「历史库为空」与「有历史但本次无相关」必须可区分的状态 | `N_检索 = 0` **不是错误**，不得返回错误码 |
| **运行时容错** | `TC-62` 失败一律可恢复、可重试、**不设产品层次数上限 / 冷却门槛**；`TC-63` 解析失败允许"仅保存原文" | **写路径必须与 AI 调用解耦**：一次 AI 失败**不得回滚已保存数据** |

## §2 A｜架构候选对比表（`TQ01` + `TQ05` 合并视角）

### 2.1 候选集合

| 候选 | 形态 | 说明 |
|---|---|---|
| **C-A** | **纯前端（无服务端）** | 浏览器 SPA + 浏览器本地存储（LocalStorage / IndexedDB），LLM 由浏览器直连 |
| **C-B** | **单体全栈（Next.js）** | Next.js App Router + Route Handlers 作为服务端；ORM → 托管 PostgreSQL；单一仓库、单一部署 |
| **C-C** | **前后端分离（SPA + 独立轻后端）** | 静态前端（SPA）+ 独立 API 服务（Node/TS 或 Python）；两级部署 |
| **C-D** | **轻量单体（单进程同源）** | 单服务进程（Hono / Fastify / FastAPI 等）+ 同源托管静态前端；容器化部署；单一部署 |
| **C-E** | **BaaS 一体化（前端 + 托管 DB + Edge Function 代理）** | 静态前端 + 托管 PG/RLS + 平台侧函数代理 LLM；业务规则部分下沉到平台配置 |

> 说明：C-A 同时覆盖"纯前端 + 本地存储"与"纯前端 + 托管 DB + 浏览器直连 LLM"两类（后者见 §3）。

### 2.2 九维度对比（优 / 中 / 差 + 判据）

| 维度 | C-A 纯前端 | C-B 单体全栈（Next.js） | C-C 分离（SPA + 独立后端） | C-D 轻量单体（单进程同源） | C-E BaaS 一体化 |
|---|---|---|---|---|---|
| **① 10 天 Demo 开发成本** | 优（最快，但**规则需重写**） | **优**（一端到底，框架内已含服务端能力） | 中（两套工程 + 跨域 + 两份配置） | 中（需自建 HTTP 层与构建集成） | 中（平台能力省事，但规则落在平台配置中难测） |
| **② 双人后续并行开发** | 差（只有一个代码面，**无服务边界**） | **优**（同仓库 + TS 类型共享；靠目录分层切分） | **优**（前后端天然可一人一侧；契约显式） | 中（同仓库，服务端边界清晰，但需自定契约机制） | 差（逻辑分散在客户端、平台配置、函数三处） |
| **③ 部署复杂度** | 优（静态托管） | **优**（单一应用一次部署） | 差（两级部署 + 环境变量 + CORS + 两套回滚） | 中（单一容器一次部署，但需容器托管能力） | 中（前端 + 平台两处配置） |
| **④ AI 调用接入** | ❌ **差（Key 必须暴露）** | **优**（服务端独占；可按步拆分为独立 Route Handler） | **优**（服务端独占；工作流集中在后端，便于串联） | **优**（服务端独占；**无 Serverless 执行时长限制**） | 中（Key 安全，但多一跳平台函数，排障链路变长） |
| **⑤ 云数据库接入** | ❌ 差（需直连 DB 或平台 SDK，凭据同样暴露） | **优**（服务端 ORM 连接托管 PG；依赖平台连接池） | **优**（同 C-B，且连接数更可控） | **优**（长驻进程连接池最省心） | 中（平台内建，但 RLS/策略与业务规则**双写**风险） |
| **⑥ 本地开发体验** | 优（无需 DB） | **优**（一条命令起全栈；DB 用托管开发实例或本地 PG） | 中（两个终端 + 两份 env） | 中（需自建；但接近生产行为） | 中（依赖平台 CLI / 远程环境，调试链路长） |
| **⑦ 在线 Demo 稳定性** | ❌ 差（**换浏览器/清缓存即丢数据**；无云端持久化） | 优（云端持久化；风险 = Serverless 冷启动 + 单次执行时长） | 优（后端长驻可避开执行时长问题；风险 = 两级服务中任一故障） | **优**（长驻进程；冷启动仅一次容器唤醒） | 中（平台侧限流/额度为不可控变量） |
| **⑧ 既有约束合规性（§1）** | ❌ **不满足**（Key 暴露 / 规则可绕过 / 无云端持久化） | 满足 | 满足 | 满足 | ⚠️ 部分（规则双写 → 单点强制困难） |
| **⑨ 与 `S03-B/C/D` 接续成本** | 高（数据层与规则层需返工） | **低** | 低（API 契约更早显式化） | 低 | 高（物理模型与规则受平台约束） |

**判定**：**C-A 直接排除**。理由三条，均为硬约束而非偏好：
1. **API Key 必然暴露**——`TQ03` 明确要求 Key 不暴露，浏览器直连与该要求正面冲突；
2. **在线 Demo 不依赖本机数据库 + 数据必须持久化**（`TC-78` / `TC-79`）——浏览器本地存储无法满足"不依赖参赛电脑"；
3. **业务规则必须不可绕过**——`TC-77`（不得绕过 `E1`–`E4`）/ `TC-13`（决策型复用门禁）/ `TC-57`（归档过滤）需要**单一强制点**；规则下放到浏览器时这些约束退化为"建议"。

## §3 B｜各方案收益 / 成本 / 风险

### 3.1 C-B｜单体全栈（Next.js）— **PROPOSED 首选**

| 项 | 内容 |
|---|---|
| **收益** | ① 单一仓库 + 单一部署 = 10 天内**最少装配成本**；② TS 端到端类型共享 → 双人契约成本最低；③ 服务端独占业务规则与 API Key；④ 每步一个 Route Handler，天然匹配 `D9` 的**逐步可寻址**要求（`TC-19`）；⑤ 平台内建函数超时/日志/预览环境，故障排查快 |
| **成本** | 引入框架范式成本（App Router / RSC 心智）；需接受"框架约定的目录与请求模型"；**须自行建立分层纪律**，否则易把业务规则写进页面组件 |
| **风险** | 🔴 **R1｜Serverless 单次执行时长 vs 单步 LLM 延迟**：若把 ⑥⑦⑧ 串在同一个请求内，可能触及平台单次执行上限 → 需 SPIKE 验证（§9.1）。**缓解**：把 ⑥/⑦/⑧ 拆为**多个 HTTP 往返**（客户端顺序驱动），仍保持"自动链条、不插入用户动作"（见 §9.3 边界）。<br>🔴 **R2｜冷启动**：免费层休眠导致演示首次访问变慢。**缓解**：演示前预热（**运维动作**，见 §6.4）。<br>🔴 **R3｜托管平台在比赛现场的网络可达性**：属 P0 实测项（关联 `SP-01`）。**缓解**：优先选择**国内可达**的托管；若不可达则换托管平台，**不得**退回"依赖参赛电脑本地服务"。<br>🟡 **R4｜Serverless + PG 连接数**：需依赖平台/DB 侧连接池（**不得**用 Redis 做会话或缓存）。 |
| **对核心闭环影响** | 无。所有 `D9` 十步均可逐步寻址；无后台任务需求。 |

### 3.2 C-D｜轻量单体单进程同源 — **PROPOSED 备用（同一分层的低成本切换目标）**

| 项 | 内容 |
|---|---|
| **收益** | ① **无 Serverless 执行时长限制** → R1 消失；② 长驻进程连接池 → R4 消失；③ 同源托管 → 无 CORS；④ 冷启动仅容器唤醒一次 |
| **成本** | 需自建 HTTP 层与静态资源托管集成；需容器化托管能力；本地/生产行为差异需自行控制 |
| **风险** | 🟡 免费容器平台同样存在空闲休眠；🟡 自建 HTTP 层 = 自建输入校验与错误分类（需显式设计与测试） |
| **关键性质** | **C-B 与 C-D 共享同一套分层、同一份 `domain/` `data/` `ai/` `contract/` 模块**，差异**仅限适配层**（`server/` 的运行时宿主）。因此 **Gate B 在 C-B / C-D 之间的选择不产生返工**——这是本文件把两者并列推荐的核心原因。 |

### 3.3 C-C｜前后端分离（SPA + 独立轻后端）

| 项 | 内容 |
|---|---|
| **收益** | ① 前后端**天然**分属两人，物理隔离最彻底；② API 契约被迫显式化，对 `TQ12` 有利；③ 后端若选 Python 生态，AI/数据科学生态更顺 |
| **成本** | 两套工程 + 两套部署 + 两套环境变量 + CORS 配置 + 两级回滚；10 天内装配成本明显高于 C-B |
| **风险** | 🔴 **契约漂移**：无类型共享时前后端易各自演化（`R-05`）；🟡 跨域与两级服务的联合排障成本；🟡 两级服务任一故障即全站不可用，演示冗余度低于单体 |
| **适用条件** | **仅当** Gate B 倾向于"两人各占一端、且需要异构后端语言"时采用。**若采用，必须强制契约先行 + 契约测试**（§7）。 |

### 3.4 C-E｜BaaS 一体化

| 项 | 内容 |
|---|---|
| **收益** | 平台内建 DB / 认证 / 函数，起步最快 |
| **风险** | 🔴 **业务规则双写**：`E1`–`E4`、决策型复用门禁、归档过滤若部分由平台策略（RLS / 策略配置）表达，则"规则唯一强制点"被破坏，且**平台策略难以被版本化测试**，直接危及 `TC-77` / `TC-13` / `TC-57` 的验收；🟡 逻辑分散三处 → 排障与交接成本高；🟡 平台额度与限流为演示不可控变量 |
| **处置** | **不作为首选**；若采用，**业务规则必须全部收敛在自有服务端代码中**，平台只承担存储与托管。 |

### 3.5 排除项登记（含 07_TECH_ARCHITECTURE.md 历史候选）

| 候选 | 处置 | 依据 |
|---|---|---|
| 纯前端 + `LocalStorage` / `IndexedDB` | ❌ 排除 | `TC-78` / `TC-79`；且 Key 暴露 |
| 浏览器直连 LLM | ❌ 排除 | `TQ03` 要求 Key 不暴露 |
| 独立 Vector DB / 嵌入向量服务 | ❌ 排除 | 阶段约束 + `R3` / `R6`（检索技术路线属 `TQ04` → `S03-D`，**不得**以独立 Vector DB 实现） |
| Redis（会话 / 缓存 / 限流） | ❌ 排除 | 阶段约束；会话以 Cookie + DB 表达 |
| Graph DB / 图推理 | ❌ 排除 | `R3`；关系用普通关系字段（契约 §1.4） |
| 队列 / 定时任务 / 后台 Worker / 异步批处理 | ❌ 排除 | `TC-21` / `TC-25` / `TC-26` / `BLK-01` |

## §4 C｜PROPOSED 推荐方案

> ⚠️ 以下为 **PROPOSED**，**不是最终技术选型**。`TQ01` / `TQ03` / `TQ05` 由 **Gate B** 人工裁决。

### 4.1 `TQ01`｜技术栈与运行形态（PROPOSED）

```
运行形态：必须有服务端（单一强制点承载业务规则与 AI 调用）
推荐    ：C-B 单体全栈
          · 单一仓库、单一部署
          · 服务端 = 应用自身的服务端能力（Route Handler 类形态）
          · 语言/类型：TypeScript 贯穿前后端（类型即契约）
备用    ：C-D 轻量单体单进程同源（同一分层，差异仅限 server 运行时宿主）
已排除  ：C-A 纯前端（Key 暴露 + 无云端持久化 + 规则可绕过）
          C-E BaaS 一体化（规则双写 → 强制点被破坏）
```

### 4.2 `TQ03`｜LLM 接入架构（PROPOSED）

```
接入路径：后端代理（服务端独占 API Key）
          ❌ 浏览器直连（Key 暴露，违反 TQ03 明确要求）
          ❌ 平台 Edge Function 代理（多一跳、排障链路变长；仅在 C-E 下被迫使用）
结构    ：
  ① Provider 抽象层（单一 LLM Client 接口）
     —— 模型/供应商策略属 TQ03 的 Gate B 裁决内容，抽象层使其可后置决定而不动业务代码
  ② 每步独立 I/O 契约（②④⑥⑦⑧⑨ 各自输入/输出结构）
  ③ 结构化输出：优先 provider 原生 JSON Schema / 受约束解码；
     服务端 schema 校验为**硬闸门**（任何 AI 输出写入前必须校验通过）
  ④ Runtime fallback：见 §4.3
```

**`TQ03` 五项必答（PROPOSED 立场）**

| 必答项 | PROPOSED 立场 |
|---|---|
| **API Key 不暴露** | Key 只存在于**服务端环境变量**；前端任何代码、任何响应体、任何日志（可被前端读取者）均不得含 Key。**不得**使用"服务端临时签发短时凭据给前端直连"的做法（属变相暴露，且使规则可绕过）。 |
| **Structured Output** | 优先**受约束解码**（原生 JSON Schema / 工具调用）；**服务端 schema 校验为硬闸门**。校验失败 = `RUNTIME` 失败 → 允许重试；**允许"仅保存原文"降级**（`TC-63`），**不得伪造解析结果**。 |
| **Runtime fallback** | 严格三层分离（`GATE` / `RUNTIME` / `ACCEPTANCE`）：① AI 失败**不回滚已保存数据**；② `N_检索 = 0` **返回成功**（非错误），且两种空态**可区分**（`TC-66`）；③ AI 不可用不影响 ①②③④⑤ 步完整可用（`TC-66`）；④ **不设产品层重试次数上限 / 冷却门槛**（`TC-62`）；⑤ 请求超时必须**显式提示可重试**，且**重试不覆盖用户已修改内容**（`TC-63`）。 |
| **响应体禁入项** | **不得**出现：任何数值化相似度 / 接近度 / 匹配度 / 分数 / 星级 / 百分比（`TC-41`）；解析质量的分级措辞（"高/低置信""完成度"，`TC-64`）；`model` / `prompt` / `token` / `temperature` / `trace id` / `latency` / `retries` / 内部检索分数（`TC-71`）。宜以**契约测试断言这些字段不存在**。 |
| **后续 `S03-C` 可实现性** | 各步 I/O 契约**先于实现冻结**（`S03-C` 只填语义与判定逻辑，不改传输形状）；`ai/` 层**不含业务规则**（不决定门槛、不做状态迁移）、**不直接写库**——AI 输出必须经 `domain/` 规则层判定后才由 `server/` 持久化。 |

### 4.3 AI 调用链与"无后台任务"的架构表达（关键）

```
用户操作（客户端主动发起每一次 HTTP 往返）
  ①  创建 Draft                      → 写库（成功即返回）
  ②  解析                            → LLM 调用 → 校验 → 写库；失败 = RUNTIME（可重试 / 可仅存原文）
  ③  用户确认/校正
  ④  生成候选失败原因（允许 0 条）    → LLM 调用 → 写库（未处理项 = unresolved 持久化）
  ⑤  保存为 Formal                   → 写库成功 = ⑥ 唯一自动触发条件（同步、幂等）
  ⑥⑦ 检索 + 比较                     → 与 ⑤ 的调用链**同步**完成；不得排队、不得后台
  ⑧  生成 Insight（candidate）        → 与 ⑥⑦ 同屏呈现
  ⑨⑩ 生成 Hypothesis / 证据追溯       → 用户裁决动作驱动
```

**硬性说明**
- 全链**无队列、无定时任务、无后台 Worker、无异步批处理**（`TC-21` / `TC-25` / `TC-26` / `BLK-01`）。
- ⑥⑦⑧ **可以在传输上拆成多个 HTTP 往返**（客户端**顺序**驱动），这在语义上仍是"同步的自动链条"；**但拆分的唯一合法理由是运行时执行时长，且不得因此插入任何 `D9` 未列出的用户动作**（`TC-22`）——该边界须由 `S03-C` 确认（§9.3）。
- **幂等**：⑤ 重复提交只产生一次 ⑥（`TC-23`）；需以请求级幂等键实现。

## §5 D｜推荐的逻辑模块边界

> 表达为**框架无关的分层**。TS 目录名只是 `TQ01` 未定情况下的默认书写形式；若 Gate B 选择其他语言，**分层与依赖方向不变**。

```
src/
├── contract/        # 🔒 跨模块共享契约（Integrator 守门，双签）
│                    #    枚举唯一字面量 · ID 规则 · 消歧常量 · 传输类型
│
├── domain/          # 纯业务规则：无 IO · 无框架 · 可独立单测
│   ├── attempt/     #   两级状态门槛（Draft→Formal）· 字段组 · 归档位 · 内容性字段集合
│   ├── insight/     #   状态迁移矩阵 · E1–E4 判定编排 · 事件日志写入决策
│   ├── hypothesis/  #   kind（grounded/model）· 裁决位 · 保存位与裁决位分离
│   ├── evidence/    #   EvidenceRef role · N_引用 派生（与 ⑩ 清单同源）
│   ├── relevance/   #   Level A/B/C 编排（⚠️ 不含检索技术实现 → S03-D）
│   └── outcome/     #   GATE / RUNTIME / ACCEPTANCE 三层 + EXIT-A/B/C 路由
│
├── data/            # 🔒 唯一数据访问层（双签）
│   ├── filters      #   ★ 单点强制注入 Draft 排除 / 归档排除（TQ23）
│   ├── schema/      #   ORM 逻辑模型（物理建模粒度 → TQ07，未定）
│   └── repos/       #   各对象存取（不得内含业务判定）
│
├── ai/              # LLM 适配：不含业务规则、不写库
│   ├── client       #   provider 抽象（模型策略 → TQ03，未定）
│   ├── steps/       #   ②④⑥⑦⑧⑨ 各步 I/O 契约实现
│   └── validate     #   schema 校验 + 失败分类（→ RUNTIME）
│
├── server/          # HTTP 边界：输入校验 · 错误分类 · 编排；不含业务规则
│   ├── routes/
│   └── errors       #   三层语义与出口的传输表达（编码 → TQ24）
│
└── ui/              # 呈现 + 触发；不做门槛判定、不自行计算 N
```

**依赖方向（单向，禁止反向）**

```
ui  →  server  →  { domain, data, ai }
                     ↑
        domain（纯规则，不依赖任何 IO）
        ai     只产出/消费结构化对象，经 domain 判定后才由 server 落库
        data   只负责存取 + 强制过滤，不含业务判定
```

**四条不可违反的分层纪律**

| # | 纪律 | 依据 |
|---|---|---|
| 1 | **门槛判定只在 `domain`**；`ui` 与 `server` 不得各自实现 | `TC-77` / `TC-13` |
| 2 | **`Draft` / 归档过滤只在 `data/filters` 注入一次**；调用方不得自行拼装过滤条件 | `TC-23` / `TC-57` / 契约 §12 第 9 项 |
| 3 | **`ai/` 不写库**：AI 输出必须经 `domain` 判定 | `D7` / `TC-12`（`source_type` 恒不变）/ `TC-26` |
| 4 | **`contract/` 是枚举与消歧常量的唯一来源**；业务代码不得重复枚举字面量 | 契约 §12 第 1、12 项 |

> ⚠️ 纪律 2 只提**实现位置建议**，**不改变契约语义**；若 Integrator 对 `TQ23` 另有收敛结论，**以 Integrator 为准**。

## §6 E｜Frontend / Backend / AI / Database 职责边界

### 6.1 职责矩阵

| 关注点 | Frontend（`ui`） | Backend（`server` + `domain`） | AI（`ai`） | Database（`data` + 托管 PG） |
|---|---|---|---|---|
| **AI API Key** | ❌ 不可见 | ✅ **独占持有**（环境变量） | 经 Backend 注入 | ❌ 无关 |
| **`D9` 步骤编排** | 触发 + 呈现 | ✅ **编排与状态推进** | 提供单步产物 | 持久化 |
| **对象门槛（`GATE`）** | 只呈现结果 | ✅ **唯一判定点** | ❌ 不得决定 | ❌ |
| **`E1`–`E4` 判定** | 只读呈现（不可编辑） | ✅ 编排 + 结构性检查（`E1`/`E4` 可机器核验） | `E2`/`E3` 等内容质量判断以 `Inference` 输出 | ❌ |
| **`E5` 与状态迁移** | 发起用户动作 | ✅ **执行迁移 + 写事件日志** | ❌ | 持久化状态与事件 |
| **决策型复用门禁** | 只呈现 `unresolved` 状态 | ✅ **唯一执行点** | ❌ | 持久化状态 |
| **`N_检索` / `N_引用`** | 只显示 `N_引用`；**不得自行计算** | ✅ 计算（`N_引用` 与 ⑩ 清单**同源**） | ❌ | 提供基础集合 |
| **`Draft` / 归档过滤** | ❌ 不可自行过滤 | 经 `data/filters` | ❌ | ✅ **单点强制注入** |
| **归档后的只读性** | 隐藏编辑入口 | ✅ 服务端拒绝编辑 | ❌ | ✅ 拒绝写入 |
| **数值相似度** | ❌ 不得渲染 | ❌ 不得传输 | ❌ 不得产出 | ❌ 不得存储 |
| **技术层字段** | ❌ 不得接收 | 可写入**独立技术通道** | 可在技术层记录 | 与产品层**物理或逻辑隔离** |
| **L4（恰 4 项）** | 呈现 4 项 | ✅ 写入 4 项 | ❌ | 持久化 |
| **检索技术实现** | ❌ | 编排 | ❌ | ❌（→ `S03-D` / `TQ04`） |
| **业务判定** | ❌ | ✅ | ❌ | ❌ **仅做过滤，不做判定** |

### 6.2 传输层边界要点（不定稿）

- **每次响应必须可区分**：正常 / `GATE`（对象门槛未满足）/ `RUNTIME`（技术失败可重试）/ 合法为空（含两种空态可区分）。**不得**用同一文案 "历史证据不足" 覆盖 `EXIT-A` / `EXIT-B` / `EXIT-C`（`TC-65`）。
- **`N_检索 = 0` 返回成功**：必须带**可区分的空态判别**（历史库为空 / 有历史本次无相关，`TC-66`）。
- **内容条目与引用为一等对象**：`source_type` / `confirmation_class` / `decision_state` / `role` **逐条随对象传输**（`TC-10` / `TC-11` / `TC-45`）。
- **`role` 必须逐条标出**（`grounding` / `support` / `contradict` / `context`），且**纯上下文不计入 `N_引用`**（`TC-44` / `TC-45`）。
- **第一入口不得是表单**：录入的第一入口必须是自然语言输入（`D-011`）；服务端**不得**以字段补全为由拒绝 ①（`TC-20`；① 唯一门槛 = 非空非纯空白）。
- **`Project` 不得作准入参数**：请求可携带 `Project` 作**解释维度**，但**不得作为检索准入过滤**（`TC-84`）。

### 6.3 传输形状不定稿声明

路由命名、协议细节、请求 / 响应体的具体形状**不在本文件定稿**（契约 §0.2：最终 API → `S03-A` / `S03-B`）。本节只锁定**职责与边界**，供 `S03-B` / `S03-C` 与 Integrator 收敛。

### 6.4 运维 / 部署动作 ≠ 运行时后台任务（消歧）

| 动作 | 归属 | 是否违反"无运行时后台" |
|---|---|---|
| 演示前预热（打开一次页面 / 触发一次请求） | **部署 / 演示运维动作** | ❌ 不违反 |
| 部署平台的健康检查 / 保活 ping | **运维动作** | ❌ 不违反 |
| 定时帮用户重跑历史比较 | **产品运行时后台任务** | ✅ **违反**（`TC-21` / `TC-25` / `BLK-01`） |
| 队列 / 异步批处理生成 Insight | **产品运行时后台任务** | ✅ **违反**（`TC-26`） |

> 该区分与 `BLK-01` 口径一致：**"Cloud Worker" = 开发期并行任务，不是运行时后台 Worker**。

## §8 G｜对 `TQ01` / `TQ03` / `TQ05` 的 Gate B 建议

> ⚠️ 以下均为 **PROPOSED 建议**，**不构成最终结论**。**技术栈最终选择属人工决策项。**

### 8.1 `TQ01`｜技术栈与运行形态

| 建议项 | PROPOSED |
|---|---|

| **推荐** | 采用 **C-B 单体全栈**；**同时接受 C-D 作为等价备用形态**（同一分层，差异仅 `server` 运行时宿主） |

| **建议排除** | C-A 纯前端（Key 暴露 + 无云端持久化 + 规则可绕过）；C-E BaaS 一体化（规则双写） |

### 8.2 `TQ03`｜LLM 接入路径与模型选型策略

| 建议项 | PROPOSED |
|---|---|
| **决策问法** | 「LLM 是否统一经**服务端代理 + provider 抽象层**接入？」「模型选型策略是**单一模型**还是**按步分级**？」 |
| **推荐（接入路径）** | **后端代理**；`ai/client` 抽象 provider；模型与供应商策略**可在不改业务代码的前提下后置替换** |

### 8.3 `TQ05`｜部署与在线 Demo 运行环境

| 建议项 | PROPOSED |
|---|---|

## §12 `TQ06`｜最小工作空间实现（PROPOSED）

**必需层级（唯一）**

```
User（V1 = 隐式单用户，无账号体系）
  └── Personal Workspace（匿名工作空间标识）
        └── Project（可缺省）
              └── Attempt（+ Insight / Hypothesis / EvidenceRef / 事件日志）
```

| 项 | PROPOSED 方案 | 说明 |
|---|---|---|
| **身份** | **匿名 Workspace 标识**：首次访问由服务端生成不可猜的 workspace 标识，作为**长期 Cookie** 持久化 | **不引入**账号 / 密码 / 邮箱验证 / 第三方登录 |
| **`User`** | V1 作为**逻辑占位**（可表现为一条隐式用户记录，或仅由 workspace 隐含） | 与 `D3` 一致：`User` 是层级顶层，但 V1 不建模团队成员 |
| **`Project`** | **存在且可缺省**；仅作组织上下文与 **Level B 解释维度** | 🔴 **不得**作为检索准入过滤（`TC-84` / `D-045` TR-10） |
| **作品空间切换** | **V1 不做**多工作空间切换 UI | 保持最小 |
| **明确不引入** | 团队成员 · 成员邀请 · 角色 · 权限 · 管理员体系 · 协同编辑 · 团队工作区 · 复杂组织结构 | `TC-02` / `D3` / 阶段约束 |

**风险与设防（对应启动文档 `R-04`）**

| 风险 | 设防 |
|---|---|
| 清 Cookie / 换浏览器导致"数据找不到"（数据仍在，但工作空间标识丢失） | ① 演示使用**固定的 Demo 工作空间**（打开即用，不依赖 Cookie 重建）；② Cookie 设长期有效期；③ 提供"用标识恢复"的极简入口（**可选**，不属产品机制） |
| 匿名标识被当作"账号体系" | 明确：**匿名单用户 ≠ 账号体系**；不引入任何身份验证与授权判定 |
| 演示现场需要登录 | **不需要**：演示工作空间**打开即用** |

> ⚠️ 本项为 **Integrator 收敛项**（`TQ06`）；本文件只出 PROPOSED 方案。若 Integrator 认为需要真实账号，**需评估"现场多一步登录"的演示风险**。
